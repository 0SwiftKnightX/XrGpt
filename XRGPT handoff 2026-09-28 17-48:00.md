# 5. Item / Inventory Architecture

A major portion of this conversation/workstream established and audited the item pipeline.

The intended authoritative chain is:

`ItemDefinition`
→ `ItemCatalog`
→ `Creative Item Index`
→ `ItemInstance`
→ `Procedural Factory`
→ `Physical Object`
→ `XR Pickup`
→ `World Placement / Drop`
→ `Re-Pickup`
→ `Inventory Return`

The critical rule is that the same authoritative `XRGptItemInstance` must survive the round trip.

It must not be silently replaced with a duplicate instance.

## Implemented item definitions

The core test catalog includes:

- Rock
- Stone
- BLACK CUBE

The item catalog was hardened into a single authoritative definition pool.

`find_definition()` rejects empty IDs.

The catalog validates:

- duplicate IDs;
- empty IDs;
- null entries;
- canonical membership.

## Inventory identity

Inventory registration validates:

- catalog-backed definition;
- non-empty owner;
- correct owner;
- valid quantity;
- authoritative max-stack range.

`XRGptItemInstance.setup()` resets durability and clamps quantity against the definition's stack limit.

## Procedural runtime

The procedural factory was hardened so generated physical objects cannot be produced from arbitrary/mismatched definitions.

The runtime verifies:

- canonical definition;
- ItemInstance identity;
- owner;
- physical object type;
- procedural pickable type;
- required Visual node;
- required CollisionShape3D.

## Pickup and return

The vendored XR Tools pickup API was inspected and preserved.

The project uses the authoritative XRToolsPickable lifecycle.

The procedural pickup layer preserves the same ItemInstance through:

- pickup;
- drop;
- world placement;
- re-pickup;
- inventory return.

Inventory return occurs only after the object has successfully entered the authoritative inventory state.

Failed placement restores the source inventory state.

Duplicate-safe inventory registration was added.

- rarity rejection;
- exclusive occupancy;
- ownership loss;
- detach cleanup;
- lifecycle signal errors;
- visual replacement failures.

## Transactional visual replacement

A concrete defect was found where exclusive occupancy could collapse into a generic incompatible-attachment result.

Another defect could detach the existing visual before replacement creation succeeded.

The fix made replacement transactional:

1. validate compatibility;
2. preserve current ownership/state;
3. attempt new visual creation;
4. only commit the replacement after success;
5. preserve the old visual/state on failure.

A dedicated Phase 1 failure-path regression suite was created.

The CI runner executes the attachment regression suite three times.

No XR Tools addon files were modified.

# 23. Production Architecture Corrections

The supplied larger production game brief contained concepts that require architectural care.

Important rules captured by the project:

## Vehicles

Do not construct a vehicle by arbitrarily reparenting independent RigidBody3Ds under another rigid body.

A vehicle needs an explicit physical ownership/assembly model.

## Tower-defense targeting

Do not use raw world Z as a generic targeting metric.

Targeting should use defined spatial/navigation/path data.

## HUD / fast travel

HUD should not own a fast-travel service.

Presentation and world travel/service logic must remain separate.

## VR + Flat

VR + flat support does not automatically mean multiplayer cross-play.

True cross-play requires:

- network authority;
- replication;
- synchronization;
- session architecture;
- input abstraction;
- state ownership.

## Quest performance

Do not assume desktop-class volumetrics/post-processing are appropriate for Quest 3S.

Quest performance must be treated as a first-class constraint.
